# PALETTE — 256 colours, one byte per pixel (D19)

Owner's decision (2026-09-19), after a run of side-by-side proofs: **every image in the game
is palettised to 256 colours and stored at one byte per pixel.** The point is not memory. It is one look
across every ChatGPT generation, and lighting, time of day and effects done as palette tables instead of
redrawn art. This file is the contract between the cutter and the engine.

## The palettes

- **`story/palette/master.hex`** — the master palette, 256 lines of `#rrggbb`, shared by everything that
  can be on screen together in the field: tiles, stamps, walkers, portraits, UI art.
  **Index 0 is transparent. Index 1 is pure black, index 2 pure white.** 253 colours are free. The palette
  is organised as material ramps (variable length: long for skin, foliage, earth, stone, roof red; short
  for rare hues), shadows hue-shifted toward blue-violet and highlights toward yellow, because ramps are
  what make the light tables degrade gracefully. `master.pal.png` (256x1) and `master_swatch.png` (the
  image attached to ChatGPT prompts, one ramp per row) are generated from the hex file.
- **Cutscene panels get their own palette per scene** (`story/panels/<scene>.hex`, generated at cut time):
  they are never lit, never share the screen with the field, and their skies need the colours. Index 0 is
  still transparent.
- The palette is versioned by a `# version N` first line. Changing it means re-running `ingest --force`:
  every shipped image is re-derived from the raw returns archived in `story/sheets/`, so the palette can
  always be revised without regenerating art.

## Conversion (the cutter's last step)

Nearest colour in **Oklab**, exact (no coarse lookup grid for shipped art). **No dithering**, anywhere:
this art is cel-shaded over generator texture and every dither mode tested made it worse. Alpha is
**hard**: a pixel whose keyed alpha is under 0.5 becomes index 0, anything else takes its nearest opaque
colour after un-matting. Shipped files are **indexed PNGs** (colour type 3, PLTE + tRNS) — one byte per
pixel on disk, viewable anywhere. Applies to `atlas.png`, walkers, field sprites, portraits and panels
alike. `./story_prompt.py palette apply <file>` converts anything by hand;
`palette build` rebuilds the master from the corpus; `palette check` fails any shipped image that holds a
colour outside its palette.

## In the engine

- An indexed PNG decodes through stb_image as RGBA; the loader maps each pixel back to its index by exact
  match against the palette (a 256-entry hash; alpha < 128 → 0) and uploads **`GL_R8`**, `GL_NEAREST`.
  A pixel that matches nothing is a build error in the art, logged once per file with a count, and takes
  the nearest colour.
- One **colormap** texture per palette: 256 wide, one row per (table, light level). Tables: `day`,
  `dusk`, `night`, the point-light table **`lamp`** (aliased `lantern`), plus effect tables (`flash`,
  `poison`, `stone`, …) as they are needed; 32 light levels
  per table, darkening in Oklab with a floor so the darkest level still reads (L never under ~0.15 for a
  colour that started above it). The colormap is generated by the tool into
  `story/palette/colormap.png` with a `colormap.json` naming the rows; the engine never computes colour.
  **`colormap.json` is the authority for which tables exist and where each row starts** — read
  `tables[].row0` and `point_light_table`; never assume an order or compute `table_index * levels`.
- **A shader never computes colour.** It fetches an index, looks it up in the colormap row for that
  fragment's light level, and draws what comes back. Light per fragment = the map's ambient
  (`light: <table> <level>` in a tmap's `## meta`) plus any point lights (`lamp:` lines, or `light`
  triggers); a fractional level blends the two adjacent rows. Where art is filtered rather than
  point-sampled, the neighbouring indices are looked up first and the **colours** are blended, with
  premultiplied alpha and index 0 = zero, so hard-alpha edges still render soft.
- The cutscene player keeps drawing panels as ordinary RGBA textures (stb expands the indexed PNG); it
  needs no change.
- Palette cycling (water, fire, lamps) is a per-frame rewrite of a few colormap columns, declared in
  `story/palette/cycles.md` as `name: indices… @ fps`.

### What the engine actually did, and the rules that came out of it

These were learned on the tile field in 2026-09-19 and every one of them still holds for the voxel
field. They are the reason the colormap is shaped the way it is.

- **Index 0 must be transparent in the colormap.** v2 writes it that way; v1 wrote the colormap as an
  opaque picture and every sprite drew inside a black rectangle. The engine checks and says so in the
  log rather than assuming either.
- **The colormap's rows run bright to dark** (`colormap.json`: "level 0 is full light, 31 the
  darkest") and the engine's built-in fallback tables are generated in that same order, so there is
  one convention.
- **A point light's pool is looked up in its own table**: `colormap.json`'s `"point_light_table"`
  (v2: `lamp`), else a table called `lamp`/`lantern`, else `day`. Row bases come from
  `tables[].row0`, never from `table_index * levels`.
- **Point lights are `lamp:` lines in a tmap's `## meta`.** A `light` trigger kind is accepted too.
- **An off-palette pixel is a warning, not a build error.** The loader counts and logs it per file and
  takes the nearest master colour, so art that has not been through the cutter still runs.
- **Night and lamp tint by ADDING a cast in Oklab and taking chroma out, never by rotating hue.**
  Rotating a red roof toward blue runs it through magenta, which is how the first night table turned
  the town pink.
- **The colormap is COLOUR, never a palette index.** Only art is palettised; the colormap ships as
  RGBA and may hold any colour at all. v2 fitted every lit colour back to its nearest master index,
  which cost up to dE 0.10 in Oklab — five times a just-noticeable difference — and, because the
  nearest entry to a lit colour is often a step of a different ramp, it jumped families: a lit blue
  (15,19,112) came back as a teal (3,34,59), and there were 373 hue breaks between *adjacent* light
  levels of the day table alone, which is a staircase the eye sees as the light slides. Fixed
  2026-09-21; the tables are now exact.
- **Row (`day`, level 0) is the palette itself, column for column** — the identity row, reserved
  cycle indices included. A reserved index's day row holds its base colour; cycling is the engine's
  per-frame rewrite of those columns, not something the generator bakes in.
- **Firelight bleaches; it does not saturate.** A lantern is a narrow warm spectrum, so a lit surface
  keeps *less* of its own hue (`LAMP_CHROMA` 0.70), and the warm cast is what carries the reading.
  v2 applied a 1.10 chroma *gain* with a cast too weak to register, so the party's lantern pool on
  night pasture was the most saturated green on the screen — neon grass — instead of the warmest
  thing on it. Grass under a lantern must read warm olive/straw.
